# Guild Bank Upload Timezone Fix — Server-Side Freshness Guard

**Date:** February 13, 2026, 11:50 PM PST
**Type:** Bug Fix
**Status:** Completed — Fix deployed and verified

---

## What Was Accomplished

Fixed a server-side bug that caused guild bank uploads to be permanently rejected when guild members in different timezones uploaded scan data.

### Problem

The `/api/guild-bank/inventory` PUT endpoint had a freshness guard that compared `scanTime` strings:

```typescript
if (body.scanTime <= existing.scanTime) {
  // SKIP — existing data is "newer"
}
```

`scanTime` is generated by the GBankExport addon's Lua `date()` function, which returns **local time** on the uploading machine with **no timezone indicator**. When guild members in different timezones upload data:

- EST user scans at 12:47 AM Feb 14 → `scanTime = "2026-02-14 00:47:17"`
- PST user scans at 11:25 PM Feb 13 → `scanTime = "2026-02-13 23:25:03"`

The PST scan is **1.5 hours newer** in real time, but the string comparison thinks it's older (`"2026-02-13" < "2026-02-14"`). Result: the PST user's uploads are permanently rejected until their local clock date rolls past the stored EST timestamp.

### Evidence from Server Logs

13 successful uploads occurred throughout the day. After an EST user's upload was stored at 21:50 PST with `scanTime=2026-02-14 00:47:17`, **every subsequent upload was rejected**:

```
21:53  SKIPPED: existing=2026-02-14 00:47:17 >= incoming=2026-02-14 00:47:17
21:57  SKIPPED: existing=2026-02-14 00:47:17 >= incoming=2026-02-14 00:31:20
22:00  SKIPPED: existing=2026-02-14 00:47:17 >= incoming=2026-02-12 21:17:24
23:25  SKIPPED: existing=2026-02-14 00:47:17 >= incoming=2026-02-13 23:25:03
23:26  SKIPPED: existing=2026-02-14 00:47:17 >= incoming=2026-02-13 23:25:03
```

The last two rejections were the user's latest scan (6236 items, 5 tabs) — more complete data than what was stored (4307 items, 4 tabs).

### Solution

Replaced the timezone-dependent `scanTime` string comparison with a **dedup-only guard** that only skips exact duplicates (same `scanTime` AND same `totalItems`). All other uploads are accepted — latest scan wins.

**Before (broken):**
```typescript
if (body.scanTime <= existing.scanTime) {
  // SKIP — timezone-dependent string comparison
}
```

**After (fixed):**
```typescript
if (body.scanTime === existing.scanTime && body.totalItems === existing.totalItems) {
  // SKIP — exact duplicate only
}
```

This is timezone-agnostic. Different scans (different scan times or different item counts) always get accepted. Only redundant duplicate uploads of the exact same scan are deduplicated.

## Root Cause Summary

The guild bank scanner **was pushing data** — the Electron app file watcher was working correctly, detecting file changes, parsing FlatData, and sending HTTP PUT requests. The **server was rejecting** every upload because a guild member in a timezone east of PST had previously uploaded data with a future-looking `scanTime` string, and the string-based freshness guard treated all PST timestamps as "older."

## Lessons Learned

1. **Never compare local timestamps across machines without timezone info.** The addon's `date()` returns bare local time — useless for cross-timezone ordering.
2. **The freshness guard was the wrong approach.** For guild bank data where "latest scan = most accurate," a simple dedup check is sufficient. Server-side `uploadedAt` (UTC) is the reliable ordering indicator.
3. **The AH & Vault Sync Electron app was working correctly throughout.** The problem was entirely server-side. The app successfully detected file changes, parsed data, and made upload requests — they were just being rejected.
